# Referral payout status

Referral rewards are backend-created records in `referralRewards`, keyed by the referred user's UID. The first transition of a referred user's purchase to approved creates one USD 10 reward with `status: available`. Existing `credited` records are treated as legacy internal credits for display and aggregation only; they are not evidence of a payment or an entitlement to withdrawal. Referral amounts do not change trading-account balances or payout eligibility.

Referral tokens use signed, unpadded URL-safe Base64 segments. The decoder rejects noncanonical payload and signature encodings, invalid signatures, malformed/oversized tokens, and invalid JSON. Attribution requires a nonempty authenticated UID, a nonempty referrer UID, no self-referral, a valid Firebase Auth creation timestamp later than the token issue time, and a Firestore transaction that permits only one attribution per referred UID. The creation-time ordering means a newly attributed user must be newer than the referrer account, preventing cycles in newly created referral chains. These checks do not repair or validate legacy attribution records.

## Current payout lifecycle

Authenticated `POST /api/payouts/requests` verifies that the Firestore account belongs to the caller and is active, then returns HTTP 503 with `payout_eligibility_unavailable`. It does not create a payout request, trust the client amount, read `withdrawableProfit` as a payout basis, reserve trading funds, or change referral rewards. Authenticated `GET /api/payouts/requests` only returns owner-scoped history for any existing records; no payout review/approval, provider submission, completion, failure, cancellation, retry, or verified event handler was found.

The read-only `GET /api/payouts/eligibility` interface always reports `unavailable` until the approved period-based net accounting inputs and remaining account policy are verified. It now also checks for open positions and reports that blocker. The trader dashboard uses this response to display payout availability and enable the request action; the Firestore `withdrawableProfit` field is not used to enable or amount a request. A successful future eligibility response would still not be sufficient to settle a payout: an authorized, auditable completion/failure workflow is also required.

## Safe boundary and next step

Referral rewards remain separate and `available` after approval. The approved policy permits them only as a separate line item in a combined request after normal payout eligibility; current eligibility is unavailable, so the dashboard and request API continue excluding them. The dashboard reports available and paid counts separately and makes clear that an available credit is not a payout. The current payout request endpoint ignores client-supplied referral amounts and reward IDs. No referral reservation, payout line item, paid transition, or failure release is implemented.

Before enabling referral amounts in payouts, establish and review (1) the authoritative, server-controlled source and rules for normal payout eligibility and (2) a trusted payout lifecycle that authenticates exact-reference/exact-amount completion and failure outcomes, handles retries and idempotency, and records auditable status transitions. Then reserve reward IDs atomically with request creation, and settle or release only on verified completion or failure respectively. Pending, timed-out, or otherwise ambiguous outcomes must retain reservations. See `PAYOUT_POLICY_DECISIONS.md` and `PAYOUT_REMAINING_WORK.md` for the decision list and dependency sequence.
